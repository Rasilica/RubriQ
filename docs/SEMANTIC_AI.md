# 요구사항 확인 후 보고서 AI 검사

`/prepare`에서 준비한 안내문·보고서를 대상으로 요구사항과 보고서 근거를 비교한다. PDF·DOCX·HWP·HWPX의 공통 원본 구조를 사용하며 PDF 미리보기 생성이 실패해도 읽은 원문 구조가 있으면 검사할 수 있다.

## 실행 순서

1. Gemini·OpenAI(GPT)·Anthropic(Claude)·[빌링AI](BILLING_AI.md) 또는 Ollama와 모델 ID를 선택한다. 클라우드 요청에는 설정에 저장한 제공자별 키를 사용하거나 일회성 키를 입력한다. 빌링AI는 빌링AI 키와 접두사 없는 모델 ID를 사용한다. [API 키 설정](AI_SETTINGS.md)에서 교체·삭제할 수 있다.
2. 안내문에서 읽은 블록과 전송 범위를 미리 확인한다. 클라우드는 안내문과 분석 지시문을 외부 제공자로 전송한다. Ollama는 설치된 로컬 모델만 사용한다. 명시적으로 실행해야 요구사항 후보가 생성된다.
3. 원문 인용과 요구사항 후보를 비교한다. 제목·필수/선택/조건부 분류·하위 조건·포함 여부를 수정한다. 조건부 항목은 적용 여부와 이유를 정하고 제외 항목은 제외 이유를 입력한다. 요구사항을 확정하기 전에는 보고서를 검사할 수 없다.
4. 확정한 기준과 안내문·보고서의 읽은 블록을 다시 미리 확인하고 검사 실행에 동의한다. 요구사항 추출 동의만으로 보고서를 자동 전송하지 않는다. 각 단계는 별도 요청·비용이다.
5. 항목별 AI 판단·이유·검증된 원문 인용을 확인한다. 근거 보기를 누르면 해당 문서의 원문 블록과 실제 PDF 문구 대응을 확인한다. 확인된 페이지 대응만 PDF 이동에 사용한다.

확정 후 기준을 수정하면 이전 결과는 현재 기준의 검사로 취급하지 않는다. 다시 확정·실행해야 한다. 입력 중인 수정이나 진행 중인 AI 요청이 있으면 문서 보관하기를 사용할 수 없다. 확정 뒤 문서 보관하기를 누르면 원본/준비 결과와 서버에서 확정한 요구사항, 그 기준에 일치하는 최신 AI 검사 결과를 함께 저장한다. 확정만 한 경우에는 기준만 저장하며, 확정 전 초안은 저장하지 않는다. 기준을 다시 확정하면 이전 검사 결과는 새 저장본에 포함되지 않는다. 기존 저장본은 불변 스냅샷으로 남는다.

새로고침·서버 재시작 뒤 보관 목록에서 직접 열면 저장 당시 기준과 검사 결과를 읽기 전용 기록으로 표시한다. 자동으로 마지막 문서를 열거나 AI를 다시 호출하지 않는다. 저장된 보고서 근거 보기로 원문과 실제 PDF 문구 대응을 다시 확인할 수 있다. 새 검사는 안내문 추출부터 별도로 실행한다. 문서만 보관한 이전 저장본도 계속 열 수 있으며 기존 검사 저장소를 마이그레이션하지 않는다. 원문/구조·해시·확정 기준·인용을 재검증하지 못한 자료는 손상 오류로 표시한다. 키·세션 토큰·임시 경로·이미지 캐시·개별 PDF 대응 조회는 저장하지 않는다. 보관 한도와 삭제 방식은 기존 문서 보관과 같다.

## 결과의 의미

확정 실패 후 추가 수정으로 오래된 revision 충돌이 발생하면, 화면은 같은 세션·초안의 현재 기준을 무료 조회한다. 조회 응답의 출처·초안·revision을 검증한 뒤 최신 revision만 반영하고 사용자 입력은 유지한다. 사용자가 확정 버튼을 다시 눌러야 수정이 반영되며 조회가 자동 확정이나 AI 재호출을 일으키지 않는다. 조회 실패·삭제·만료·오래된 응답이면 확정되지 않은 수정의 저장 차단을 유지한다.

내용이 바뀐 확정 기준은 초안당20버전까지다. `version_limit`은 다른 창 충돌과 구분해 한도와 새 추출 필요를 안내한다. 새 추출에는 별도 미리보기·동의와 AI 호출이 필요하다. 조건 적용 미결정 등 알려진422 검증 거절은 서버에 커밋되지 않으므로 첫 미수정 초안의 문서-only 보관 가능 상태를 복원한다. 이미 수정한 입력은 계속 확정 후 보관하며, 알 수 없는 오류나 통신/5xx 실패에서는 처리 여부가 불확실하므로 저장을 차단한다.

확정 요청은 AI를 호출하지 않는다. 서버가 확정했지만 응답을 받지 못했다면 입력을 유지한 채 같은 항목으로 무료 재시도할 수 있다. 같은 초안의 현재 확정과 항목이 완전히 같고 요청 revision이 미래가 아니면 현재 확정을 반환한다. 버전을 추가하거나 기존 검사 결과를 지우지 않는다. 화면도 변경 없는 확정 버튼을 비활성화한다. 다른 내용의 오래된 요청은409 충돌이며 수정 내용은 유지한다. API 키 설정의 상태 알림은 진행 중인 무료 확정을 취소하지 않는다.

검사 결과 없이 확정 기준만 보관할 때에는 안내문·기준·인용·해시를 검증한다. 보고서가 AI 검사 한도를 넘거나 읽지 못했어도 문서 보관 계약을 만족하면 저장·재열기가 가능하다. AI 검사에는 아래60,000자·500블록 한도를 계속 적용하며 초과 문서를 자르지 않는다. 검사 결과를 포함하는 보관은 보고서 출처·범위·근거와 검사 예산도 검증한다.

| 표시 | 의미 |
|---|---|
| 충족 근거 발견(AI) | 해당 조건을 뒷받침한다고 AI가 판단한 원문 인용이 있음 |
| 일부 충족(AI) | 하위 조건 중 근거를 찾은 항목과 미확인 항목이 함께 있음 |
| 근거 미발견 | 읽고 검사한 범위에서 관련 근거를 찾지 못했다는 AI 판단 |
| 판정 보류 | 읽기/검토 범위·인용·규칙 확인 등으로 결론을 확정할 수 없음 |
| 검사 제외 | 사용자가 확정한 기준에서 제외하거나 조건이 적용되지 않음 |

서버가 검증하는 것은 출처·범위·원문 인용의 정확한 일치다. 인용이 요구사항을 의미적으로 충족하는지, AI가 전체 문서를 실제로 검토했는지, 안내문의 모든 요구사항을 추출했는지는 보장하지 않는다. 제목/목차만으로 충족을 확정하지 않으며 명시적 위반 주장도 별도의 규칙 검증 전에는 보류한다. 읽기 누락이 있는 문서의 근거 부재를 미충족으로 단정하지 않는다. 점수나 합격을 보장하지 않는다.

원본 PDF의 페이지와 편집 형식의 변환 PDF 페이지는 다르다. 중복 문구·대응 실패·변환 실패가 있으면 위치를 추정해서 강조하지 않는다. 원문 인용은 확인할 수 있어도 PDF의 페이지 대응은 미확인일 수 있다.

## 한도와 데이터 경계

- 안내문 추출은 최대 20,000자·200블록, 비교는 안내문/보고서 원문과 원래 요구사항·수정 기준의 합계 최대 60,000자·원문 500블록이다. 초과 시 오류를 반환하며 일부만 몰래 잘라 전송하지 않는다.
- 요구사항은 최대 30개, 항목별 하위 조건은 최대 10개다. JSON 응답은 기존 원문 인용 검증기를 통과해야 한다. 잘못된 JSON·인용·출처·기준 해시는 성공으로 표시하지 않는다.
- 생성 출력은 요청당 최대 8,192토큰이며 응답 크기와 시간 제한을 적용한다. 공급사/모델별 문맥 길이·추론 특성에 따라 더 작은 문서도 실패할 수 있다. 실패 시 다른 모델이나 제공자로 자동 전환하지 않는다.
- 빌링AI의 추출·검사는 공식 Responses 경로의 JSON 객체 출력 옵션을 사용한다. 문법 형식을 지정해도 출처·스키마·원문 인용 검증은 계속 적용한다. JSON 배열·설명문·코드 블록·손상 JSON을 추측 복구하지 않는다. 빌링AI 일반 윤문은 기존 Chat Completions를 유지한다. 자세한 전송 계약과 공식 자료는 [빌링AI 연결](BILLING_AI.md)을 따른다.
- 일회성 API 키는 요청 인증 헤더로 전달하고 저장한 키는 서버가 운영체제 보안 저장소에서 읽는다. 클라우드 API는 외부 전송이며 제공자 데이터 보관 조건과 과금 정책을 따른다. 브라우저 취소가 외부 추론·비용을 취소한다고 보장하지 않는다.
- 문서 내용은 분석 자료이며 명령으로 실행하지 않는다. 모델에 파일 접근·셸 실행·웹 탐색 도구를 제공하지 않는다. 사용자 원문과 AI 제안을 자동 수정하지 않는다.

## API

보고서 검사 요청의 `expected_items`는 포함·적용된 기준의 requirement_id와 하위 조건ID 순서를 명시한다. 모델은 이 순서대로만 응답 항목을 생성하도록 지시받으며 서버는 기존 계약으로 다시 검증한다. 원본 요구사항·제외 기준 문맥과 기준 해시는 유지한다. 참고 인용의 부가 정보를 응답 citation으로 복사하지 않도록 구분하고, 검증 완료 API의 citation에는 block_id·quote·char_range만 허용한다. 모델 전송용 인용 참조는 아래 설명을 따른다.

보고서 계약 실패의 서버 로그에는 고정 오류 코드와 세부 분기(code/branch), 최대5개의 정제된 스키마 오류(type/path)를 추가한다. 경로는 고정 스키마 필드명과 제한된 배열 인덱스만 남기며 알 수 없는 필드명은 extra로 대체한다. 원문 값·예외 메시지·Pydantic input/msg/ctx는 기록하지 않는다. 공개 `error.diagnostic`의 세 필드와 영구 보관 계약은 유지한다.

보관본의 `저장한 기준으로 새 검사 준비`는 위탁 AI 호출 없이 기존 현재 기준 GET으로 저장된 확정 기준을 검증해 재사용한다. 과거 기록은 별도로 유지하며 새 검사에는 다시 범위 확인·동의가 필요하다. 현재 작업 기준이 있으면 저장 기준으로 되돌아가지 않는다. 최신 확정 버전만 보관된 경우에도 원래 버전 번호와20버전 한도를 유지한다.

의미 검사 실패에는 기존 `error.code`·HTTP 상태 외에 선택적 `error.diagnostic`이 포함된다. 형식은 `{id, stage, reason}`이며 ID는32자리 소문자16진수, 단계와 사유는 고정 목록이다. 화면은 검증된 사유만 한국어로 표시하며 알 수 없는 진단은 일반 실패로 처리한다. 출력 한도 종료·JSON 해석·응답 형식·인용 검증·최종 결과 구성을 구분하고 잘린 응답을 성공으로 취급하지 않는다. 서버의 진단 로그는 ID·고정 분류·상태·바이트 수·소요 시간·검증된 사용량으로 제한한다. 키·문서·프롬프트·공급사 응답 원문·예외 문자열은 기록하지 않으며 진단은 영구 문서 스냅샷에 포함하지 않는다. 실패 후 자동 재시도는 없다.

무료 현재 기준 조회는 `GET /api/document-pairs/{session_id}/ai/criteria?draft_id=...`다. 기존 세션 토큰과 `X-Local-Client: prepare`, Host·동일 출처·요청 제한·`no-store`를 적용한다. 초안 ID는1~128자로 제한하며 조회 직전 삭제·만료·중간 커밋을 다시 검사한다. API 키 조회·AI 호출·기준/검사 결과 변경은 없다.

같은 임시 문서 세션 아래 `POST /api/document-pairs/{session_id}/ai/requirements`, `/ai/criteria`, `/ai/check`를 제공한다. 세션 토큰과 `X-Local-Client: prepare`를 검사한다. 클라우드 추출/검사는 일회성 `X-AI-API-Key` 또는 `use_saved_key: true`와 전송 동의가 필요하며 Ollama는 키가 필요 없다. 기준 확정은 모델을 호출하지 않는다.

서버는 현재 기준과 검증된 검사 결과를 세션의 임시 메모리에 보관한다. 사용자가 명시적으로 보관하기를 누른 경우에만 문서 보관 SQLite의 불변 스냅샷에 포함한다. 서버는 브라우저가 보낸 검사 결과를 저장하지 않고 실제 문서와 서버의 확정 기준·최신 결과를 대조한다. 진행 중 삭제·만료·기준 변경 이후 반환된 결과는 현재 상태로 등록하지 않는다. 재열린 기록은 새 임시 세션의 당시 기록이며, 새 AI 작업이 커밋되면 과거 기록과 현재 상태를 분리한다.

실제 키·로컬 모델이 없는 검증에서는 합성 문서와 시험용 공급사 응답을 사용한다. 이는 실제 생성 품질·계정 권한·과금·성능 검증을 대신하지 않는다. 실제 작성 자료의 호환성 평가와 AI 의미 정확도 평가는 별도 수행한다.
# 모델 전송 ID와 인용 위치

빌링AI 보고서 검사에는 요청별 `citation_ref`를 사용한다. 서버가 비어 있지 않은 보고서 블록의 원문 구간에 참조를 붙이고, 모델은 해당 참조만 선택한다. 일반 블록은 전체를,10,000자를 넘는 블록은4,000자 이하의 연속 구간을 후보로 제공한다. 인용 후보가 문장 단위라는 보장은 없다. 서버는 알려진 참조를 실제 block_id·quote·char_range로 복원한 뒤 기존 엄격한 원문·범위·검사 계약을 다시 검증한다. 참조는 요청 메모리에만 존재하며 저장 계약에는 추가하지 않는다. 모델의 의미 판단은 여전히 사용자 검토 대상이다.

이 전송 형식은 빌링AI 보고서 검사에만 적용한다. 다른 제공자와 요구사항 추출의 기존 형식은 유지한다. 모델에 주는 wire 응답 스키마에서 citation은 `{citation_ref}`이며, 검증 완료 API/보관 데이터의 인용은 기존3필드 형식이다. 알 수 없는 참조·추가 필드·엉뚱한 위치의 참조 객체는 임의로 복원하지 않는다. reviewed_block_ids는 기존 bN 블록 ID이며 qN 인용 참조와 구분한다. 복원 후 응답 크기와 키 포함 여부도 검사한다.

기존 직접 인용의 위치 복원은 문구가 해당 블록에 정확히 한 번 존재할 때만 수행한다. 잘못된 정수 범위(0–0 등)도 실제 원문 검색으로 확정할 수 있도록 보완했으며 문자열/불리언 좌표·없는 문구·모호한 반복은 계속 거절한다. 원문 불일치 진단은 블록 없음·범위 오류·문구 불일치로 구분하고 실제 문구/좌표 값은 로그에 남기지 않는다. 과거 실제 응답을 보관하지 않았으므로 과거 실패가0–0 범위였다고 단정하지 않는다.

모델에 전송하는 본문 블록은 짧은 임시 ID(`b0` 등)와 Unicode 길이를 사용한다. 응답의 ID는 서버가 해당 요청의 원래 블록 ID로 복원한다. 자료의 출처 ID와 해시 검증은 기존 계약을 따른다.

인용 문자 위치가 원문과 다르더라도 해당 블록에서 인용문이 정확히 한 번만 발견되면 서버가 실제 Unicode 범위를 확정한다. 겹치는 반복도 여러 후보로 취급한다. 없는 문구·알 수 없는 블록·모호한 위치는 임의로 복원하지 않으며 기존 엄격한 인용 검증에서 거절한다. 이 처리는 인용 원문 존재만 확인하며 의미 판단의 정확성을 검증하지 않는다.
